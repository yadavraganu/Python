01 / Foundations

Decorator fundamentals

A decorator is a callable that receives an object—commonly a function or class—and returns a replacement or modified object. The common function-decorator pattern returns a wrapper that adds behavior before, after or around the original call.

Why decorators are possible

Python functions are first-class objects. A function can be assigned to a variable, passed as an argument, returned from another function, stored in a data structure and inspected at runtime. A decorator uses these capabilities to separate cross-cutting behavior from a function's core business logic.

Input

The original callable, often named func. It may be a plain function, method function, coroutine function or callable object.

Transformation

The decorator may construct a wrapper, register the callable, attach attributes, mutate a class or return a descriptor/callable proxy.

Manual decoration

Python · no special syntax
def make_pretty(func):
    def wrapper():
        print("I am being decorated!")
        func()
    return wrapper


def ordinary_function():
    print("I am an ordinary function.")

# Explicitly replace the original name with the decorated callable.
decorated_func = make_pretty(ordinary_function)
decorated_func()

Output:

Console
I am being decorated!
I am an ordinary function.

The @ form

Python · equivalent syntax
@make_pretty
def ordinary_function():
    print("I am an ordinary function.")

ordinary_function()

The decorated definition is equivalent to ordinary_function = make_pretty(ordinary_function). The name is rebound to the decorator's returned object. The original function object still exists if another reference to it was retained, or is reachable through __wrapped__ when the decorator uses functools.wraps.

✓

Important generalization. “A decorator returns another function” describes the most common wrapper pattern, not the full language rule. A decorator must return a callable-compatible replacement for the use case, but class decorators, descriptor-producing decorators such as property, and registration decorators demonstrate that the returned object need not be a plain Python function.

02 / Runtime model

Execution & evaluation model

The most important distinction is between applying a decorator and later invoking the decorated callable. Decoration is part of executing the definition statement; wrapper logic typically runs when the resulting object is called.

Function definition lifecycle
Execute defBuild function object
→
Evaluate decoratorApply transformation
→
Rebind nameStore replacement
→
Call laterWrapper behavior
At module scope, the definition usually runs during import. Inside another function, it runs when execution reaches that nested definition.

Definition time versus call time

Python · observe when each line runs
def announce(func):
    print(f"Decorating {func.__name__}")  # definition/decorating time

    def wrapper(*args, **kwargs):
        print("Wrapper runs now")           # call time
        return func(*args, **kwargs)

    return wrapper

@announce
def greet():
    print("Hello")

print("Between definition and call")
greet()

The Decorating greet message appears while Python executes the decorated definition, before the later call. Only the wrapper's body is deferred. “At import time” is a useful module-level shorthand, but technically the rule is when execution reaches the definition; imports are merely one common place that happens.

Decorator application and stacking

For stacked decorators, the bottom decorator is applied to the original function first, then the next decorator wraps that result. The language reference describes this as nested application.

Stacked decorator call path
@outerApplied last · outer wrapper
↓ invocation enters outer layer
@innerApplied first · inner wrapper
↓
Original functionCore implementation
Application order: bottom-up. Call-time entry: outside-in. Return unwinds in the reverse direction.
!

Side effects to avoid. A decorator can execute code during module import. Avoid opening database connections, making remote API calls, loading large datasets or doing environment-dependent work while applying decorators. Prefer lightweight registration and defer external work until invocation or explicit application startup.

The formal rewrite

Equivalent nested application
@outer(config="x")
@inner
def run():
    ...

# Conceptual equivalent:
def run():
    ...
run = outer(config="x")(inner(run))

The decorator expression is evaluated in the scope containing the definition. Its result is called with the function object as its sole positional argument. The returned object is bound to the function name. A decorated name can therefore refer to an object whose type and behavior differ from the original function.

03 / Core implementation

Arguments, return values & metadata

A general-purpose wrapper must preserve the wrapped callable's calling convention, return value, exception behavior and useful metadata. The standard starting point is *args, **kwargs and functools.wraps.

The three common failure modes

ProblemIncorrect patternCorrect principle
ArgumentsWrapper accepts no parameters while the target does.Forward positional and keyword arguments transparently.
Return valueCall target but discard its result.return func(*args, **kwargs).
MetadataWrapper exposes its own name/docstring.Use @wraps(func) and retain the wrapped chain.
ExceptionsCatch and suppress all errors without a contract.Propagate by default; handle only explicitly intended exception classes.

A robust synchronous template

Python · reusable wrapper template
from functools import wraps
from time import perf_counter
import logging

logger = logging.getLogger(__name__)

def timed(func):
    """Log elapsed wall-clock time and preserve the function contract."""
    @wraps(func)
    def wrapper(*args, **kwargs):
        started = perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            elapsed = perf_counter() - started
            logger.info("%s completed in %.4fs", func.__qualname__, elapsed)
    return wrapper

@timed
def transform_batch(rows, *, strict=False):
    return [row for row in rows if row is not None]

result = transform_batch([1, None, 2], strict=True)

try/finally records elapsed time on both success and failure. The decorator does not change the exception: a raised exception continues propagating after the finally block. In production, use a configured logger rather than printing to stdout.

What functools.wraps does

wraps(wrapped) is a convenience decorator around update_wrapper. By default, it copies selected attributes such as module, name, qualified name, annotations, type parameters and docstring; updates the wrapper's attribute dictionary from the wrapped callable; and adds __wrapped__, pointing to the immediate wrapped object.

Python · introspection
from functools import wraps
from inspect import signature, unwrap

def audit(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@audit
def load_table(table: str, limit: int = 100) -> list[dict]:
    """Load rows from a logical table."""
    return []

print(load_table.__name__)              # load_table
print(load_table.__doc__)               # original docstring
print(signature(load_table))            # (table: str, limit: int = 100) -> ...
print(unwrap(load_table) is load_table.__wrapped__)  # True
i

Metadata is not magic. wraps improves introspection, but the wrapper still accepts *args, **kwargs at runtime. It does not automatically enforce the original signature or make a type checker infer every transformation. Use type annotations such as ParamSpec and TypeVar for static typing.

04 / Parameterized decorators

Decorator factories & optional arguments

When the decorator itself needs configuration—retry count, timeout, permission name, cache size or metric label—an outer function acts as a factory and returns the actual decorator.

Three-layer pattern

A configured decorator has three layers
Factoryretry(attempts=3)
captures configuration
↓ returns
Decoratordecorate(func)
receives target callable
↓ returns
Wrapperwrapper(*args, **kwargs)
executes on invocation
Python · configurable repeat factory
from functools import wraps

def repeat(times):
    if times < 1:
        raise ValueError("times must be at least 1")

    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            results = []
            for _ in range(times):
                results.append(func(*args, **kwargs))
            return results
        return wrapper
    return decorator

@repeat(times=3)
def greet(name):
    print(f"Hello, {name}!")
    return name

names = greet("Ada")

The result contract here is intentionally a list of three results. That is a behavior change from the original function's single result and should be clearly documented. A decorator should not silently change the return shape unless that is its explicit purpose.

Support both @decorator and @decorator(...)

Python · optional decorator arguments
from functools import wraps

def repeat(func=None, *, times=1):
    if times < 1:
        raise ValueError("times must be at least 1")

    def decorate(target):
        @wraps(target)
        def wrapper(*args, **kwargs):
            result = None
            for _ in range(times):
                result = target(*args, **kwargs)
            return result
        return wrapper

    return decorate if func is None else decorate(func)

@repeat
def run_once():
    print("once")

@repeat(times=2)
def run_twice():
    print("twice")

With bare @repeat, Python passes the function directly as func. With @repeat(times=2), the factory is called first, so func remains None and the factory returns the real decorator.

!

Closures capture configuration. The wrapper refers to values in the enclosing scope. Treat decorator configuration as immutable after decoration, validate it when constructing the decorator, and avoid capturing mutable global settings that may change unexpectedly. The configuration expression is evaluated at decoration time, not automatically re-read on every invocation.

05 / Composition

Stacking decorators & ordering

Decorator order is function composition. It can change return values, side-effect order, exception boundaries, authentication behavior, caching, timing and transaction scope.

Python · output of stacked decorators
def bold(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        return f"<b>{func(*args, **kwargs)}</b>"
    return wrapper

def italic(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        return f"<i>{func(*args, **kwargs)}</i>"
    return wrapper

@bold
@italic
def greet():
    return "Hello"

print(greet())  # <b><i>Hello</i></b>

The definition is equivalent to greet = bold(italic(greet)). At call time, the outer bold wrapper runs first and calls the inner italic wrapper.

Order is architectural, not cosmetic

CombinationTypical consequenceDecision point
@cache outside @timedCache hits may bypass the timed inner wrapper.Do you want timing of every request or only cache misses?
@timed outside @cacheTiming includes cache lookup and cached return path.Measure observed call latency.
@auth outside @cacheAuthorization runs before cached data can be returned.Usually safer when output depends on permissions.
@cache outside @authA cache hit may skip the inner authorization check.Potential security defect unless cache key and policy enforce isolation.
@retry outside @transactionEach retry can establish a fresh transaction if the transaction wrapper encloses one call.Ensure failed attempts roll back and retries are safe.
@transaction outside @retryRetries may happen inside one transaction scope.Often wrong when the transaction is already aborted or unusable.
✓

Interview rule. State the exact rewrite first, then reason from the outermost wrapper inward. Never guess order from the decorator names alone; inspect what each wrapper returns and which layer owns the side effect.

06 / Object model

Decorating methods & understanding descriptors

A function stored in a class namespace is a descriptor. When accessed through an instance, its __get__ behavior creates a bound method that supplies the instance as the first argument. This explains why function-based decorators usually work on instance methods, while callable decorator instances may need descriptor behavior of their own.

Function decorator on an instance method

Python · self passes through args
from functools import wraps

def log_call(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        print(f"Calling {func.__qualname__}")
        return func(*args, **kwargs)
    return wrapper

class Greeter:
    @log_call
    def greet(self, name):
        return f"Hi, {name}"

print(Greeter().greet("Mira"))

When Greeter().greet("Mira") is evaluated, Python binds the wrapper function to the instance. The instance becomes the first element of args, so the wrapper does not need to know whether it is wrapping a standalone function or a method.

Descriptor protocol essentials

MethodRoleDescriptor category
__get__(self, obj, owner)Computes/returns an attribute value when accessed.Non-data descriptor if this is the only protocol method.
__set__(self, obj, value)Controls attribute assignment.Data descriptor.
__delete__(self, obj)Controls attribute deletion.Data descriptor.

In normal instance lookup, data descriptors have priority over the instance dictionary; instance attributes are checked before non-data descriptors. Functions are non-data descriptors, which is the mechanism behind automatic method binding. property, staticmethod and classmethod are descriptor-based tools.

Decorator ordering with method descriptors

For a conventional wrapper that expects a normal function, place it closest to the function so it decorates the raw function before classmethod or staticmethod converts it to a descriptor.

Python · conventional ordering
class Factory:
    @classmethod
    @log_call
    def from_config(cls, config):
        return cls()

    @staticmethod
    @log_call
    def normalize(value):
        return value.strip().lower()

    @property
    @log_call
    def status(self):
        return "ready"
i

Do not overgeneralize decorator order. The safe ordering depends on the specific decorators. The standard abc.abstractmethod documentation explicitly says it should be the innermost decorator when combined with descriptors. Some standard decorators deliberately support nesting in particular orders; for example, singledispatchmethod must be outermost to expose its register API.

Why a callable class decorator may fail on methods

A normal function has descriptor binding. An instance of a class implementing only __call__ does not automatically gain the same method-binding behavior. Applying that instance as a method decorator can therefore result in a missing self argument.

Python · descriptor-aware callable decorator
from functools import update_wrapper
from types import MethodType

class CountCalls:
    def __init__(self, func):
        update_wrapper(self, func)
        self.func = func
        self.num_calls = 0

    def __call__(self, *args, **kwargs):
        self.num_calls += 1
        return self.func(*args, **kwargs)

    def __get__(self, instance, owner=None):
        if instance is None:
            return self
        return MethodType(self, instance)

class Worker:
    @CountCalls
    def process(self, item):
        return item.upper()

worker = Worker()
worker.process("batch")  # self is correctly bound

For method decorators, the simpler and usually preferable design is a function decorator whose wrapper is itself a function. Reach for a descriptor-aware class-based decorator only when persistent decorator state justifies the added complexity.

07 / Asynchronous callables

Async functions, generators & context managers

A wrapper must match the execution semantics of the callable it decorates. A normal call to an async def function creates a coroutine object; its body runs when awaited. A normal wrapper that times only the call therefore measures coroutine creation, not the awaited work.

Correct async wrapper

Python · await the coroutine
import asyncio
from functools import wraps
from time import perf_counter
import logging

logger = logging.getLogger(__name__)

def async_timed(func):
    @wraps(func)
    async def wrapper(*args, **kwargs):
        started = perf_counter()
        try:
            return await func(*args, **kwargs)
        finally:
            logger.info("%s took %.4fs", func.__qualname__,
                        perf_counter() - started)
    return wrapper

@async_timed
async def fetch_page():
    await asyncio.sleep(0.2)
    return {"status": "ok"}

async def main():
    result = await fetch_page()
    print(result)

asyncio.run(main())

The wrapper is also declared with async def, and awaits the original coroutine. This keeps inspect.iscoroutinefunction useful for this decorated callable and measures the awaited operation's elapsed wall-clock time.

One decorator can branch by callable kind

Python · sync and coroutine functions
import inspect
from functools import wraps
from time import perf_counter
import logging

logger = logging.getLogger(__name__)

def timed(func):
    if inspect.iscoroutinefunction(func):
        @wraps(func)
        async def async_wrapper(*args, **kwargs):
            started = perf_counter()
            try:
                return await func(*args, **kwargs)
            finally:
                logger.info("%s took %.4fs", func.__qualname__,
                            perf_counter() - started)
        return async_wrapper

    @wraps(func)
    def sync_wrapper(*args, **kwargs):
        started = perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            logger.info("%s took %.4fs", func.__qualname__,
                        perf_counter() - started)
    return sync_wrapper

This handles ordinary Python functions and coroutine functions. It does not automatically handle every custom callable that returns an awaitable, asynchronous generators or synchronous generators. Use the appropriate wrapper shape for each callable kind, or explicitly constrain what the decorator accepts.

Generators and asynchronous generators

Target callableCall returnsExecution timingWrapper strategy
Normal defValue / resultDuring callNormal def wrapper
async defCoroutine objectWhen awaited/scheduledasync def wrapper and await
Generator function with yieldGenerator objectDuring iterationGenerator wrapper, usually yield from
Async generator with yieldAsync generator objectDuring async forAsync-generator wrapper and async for
Python · measure generator iteration, not creation
from functools import wraps
from time import perf_counter
import logging

logger = logging.getLogger(__name__)

def timed_generator(func):
    @wraps(func)
    def wrapper(*args, **kwargs):
        started = perf_counter()
        try:
            yield from func(*args, **kwargs)
        finally:
            logger.info("%s iteration took %.4fs", func.__qualname__,
                        perf_counter() - started)
    return wrapper

yield from delegates iteration and forwards generator protocol operations to the subgenerator. A plain wrapper that simply returns the generator object only measures generator creation. Async-generator wrappers need async def with async for/yield; note that a simple async-for relay does not forward every asend()/athrow() interaction in the same way as direct delegation.

Decorator-like context management

contextlib.contextmanager turns a generator function with one yield into a context-manager factory. asynccontextmanager provides the corresponding asynchronous form. Context managers can also be used as decorators via ContextDecorator and AsyncContextDecorator.

!

Python 3.15 behavior change. In Python 3.15, contextlib's ContextDecorator keeps the context open for the lifetime of a decorated generator/coroutine/async-generator operation rather than closing it immediately after the generator or coroutine object is created. Earlier Python versions behaved differently. Do not assume 3.15 semantics when deploying on older runtimes.

08 / Class-level transformations

Class decorators & class-based decorators

These terms sound similar but refer to different designs. A class decorator is applied to a class definition. A class-based decorator uses an instance of a class as the decorator for a function.

PatternDecoratesTypical resultExample
Class decoratorA class objectModified/replaced class@dataclass, custom registration
Class-based function decoratorA function/callableCallable instance storing stateCall counter, memoizer object

Class decorator example

Python · attach behavior to a class
def add_greeting(cls):
    cls.greeting = "Hello from a class decorator"
    return cls

@add_greeting
class Widget:
    pass

print(Widget.greeting)

@dataclass is a standard-library class decorator. It examines annotations and adds generated methods such as __init__, __repr__ and __eq__ according to its options. It is not a function wrapper around each method.

Class-based decorator with state

Python · per-decorated-function state
from functools import update_wrapper

class CountCalls:
    def __init__(self, func):
        update_wrapper(self, func)
        self.func = func
        self.num_calls = 0

    def __call__(self, *args, **kwargs):
        self.num_calls += 1
        print(f"Call {self.num_calls} of {self.func.__name__}")
        return self.func(*args, **kwargs)

@CountCalls
def say_hello():
    print("Hello")

say_hello()
say_hello()
print(say_hello.num_calls)  # 2

__init__ runs when the class is instantiated during decoration; __call__ runs on each invocation. Each decorated function receives a distinct decorator instance. If a callable class is used on methods, it needs descriptor support as discussed in the previous section.

!

Concurrency note. Shared mutable state such as a call counter may be updated concurrently by multiple threads. If the count must be exact, protect the increment with a lock. Do not hold that lock while executing the wrapped function unless serializing the target itself is an explicit requirement.

09 / Tooling & contracts

Typing, introspection & callable contracts

A wrapper that uses *args, **kwargs is flexible at runtime, but a static type checker may not be able to preserve the original callable signature unless the decorator is typed appropriately.

Use ParamSpec and TypeVar

Python 3.10+ · signature-preserving type shape
from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar

P = ParamSpec("P")
R = TypeVar("R")

def traced(func: Callable[P, R]) -> Callable[P, R]:
    @wraps(func)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        print(f"Calling {func.__qualname__}")
        return func(*args, **kwargs)
    return wrapper

@traced
def calculate(a: int, b: int, *, strict: bool = False) -> int:
    return a + b

ParamSpec represents a callable's parameter specification and TypeVar represents its return type. For Python 3.9 and earlier, this typing pattern requires compatibility support such as typing_extensions, or the decorator can be left less precisely annotated.

When a decorator adds or removes a parameter

Use Concatenate with ParamSpec when the transformation changes the signature in a statically describable way, such as injecting a lock or request context. Do not claim the signature is unchanged if the decorator changes the call contract.

11 / Production patterns

Production-ready decorator patterns

The best decorators implement a narrow, explicit policy and preserve the target's contract. The examples below are reusable starting points, not substitutes for an application's transaction, security or observability design.

Bounded retry with exponential backoff and jitter

Retries are useful for transient failures such as a connection reset or temporary service unavailability. They are dangerous when they repeat non-idempotent side effects. A production retry policy needs bounded attempts, exception filtering, delay strategy, observability and a clear idempotency contract.

Python · synchronous retry factory
import random
import time
from functools import wraps
import logging

logger = logging.getLogger(__name__)

def retry(max_attempts=3, exceptions=(TimeoutError, ConnectionError),
          base_delay=0.5, max_delay=8.0, jitter=True):
    if max_attempts < 1:
        raise ValueError("max_attempts must be >= 1")
    if base_delay < 0 or max_delay < 0:
        raise ValueError("delays must be non-negative")

    def decorate(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, max_attempts + 1):
                try:
                    return func(*args, **kwargs)
                except exceptions:
                    if attempt == max_attempts:
                        logger.exception("%s failed after %d attempts",
                                         func.__qualname__, attempt)
                        raise
                    delay_cap = min(max_delay,
                                    base_delay * (2 ** (attempt - 1)))
                    delay = random.uniform(0, delay_cap) if jitter else delay_cap
                    logger.warning("Retrying %s after attempt %d in %.2fs",
                                   func.__qualname__, attempt, delay)
                    time.sleep(delay)
        return wrapper
    return decorate

Use it only on an operation whose retry semantics are understood:

Python · use with an idempotent operation
@retry(max_attempts=4, exceptions=(TimeoutError,))
def read_manifest(uri):
    return object_store.get(uri)

# For a write, use an idempotency key or a conditional/transactional write.
@retry(max_attempts=3, exceptions=(TimeoutError,))
def publish_partition(partition_id, idempotency_key):
    return sink.write_partition(partition_id,
                                idempotency_key=idempotency_key)
!

Retry safety checklist. Does the call have externally visible side effects? Can the same request be safely repeated? Is a timeout ambiguous (the server may have completed the operation)? Is there an idempotency key, unique constraint, conditional write or transactional boundary? Are retryable exceptions narrow? Are the total attempts and worst-case delay bounded?

Async retry

Python · asynchronous retry pattern
import asyncio
import random
from functools import wraps

def async_retry(max_attempts=3, exceptions=(TimeoutError,)):
    if max_attempts < 1:
        raise ValueError("max_attempts must be >= 1")

    def decorate(func):
        @wraps(func)
        async def wrapper(*args, **kwargs):
            for attempt in range(1, max_attempts + 1):
                try:
                    return await func(*args, **kwargs)
                except exceptions:
                    if attempt == max_attempts:
                        raise
                    delay = min(8.0, 0.5 * (2 ** (attempt - 1)))
                    await asyncio.sleep(random.uniform(0, delay))
        return wrapper
    return decorate

Do not catch BaseException broadly. In modern asyncio, cancellation is part of control flow and should normally propagate. The default Exception-derived transient failures do not swallow cancellation.

Validation decorator

Python · validate at the function boundary
from functools import wraps

def require_non_empty_argument(argument_name):
    def decorate(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            if argument_name in kwargs:
                value = kwargs[argument_name]
            else:
                raise TypeError(
                    f"{argument_name!r} must be passed by keyword"
                )
            if value is None or value == "":
                raise ValueError(f"{argument_name} cannot be empty")
            return func(*args, **kwargs)
        return wrapper
    return decorate

@require_non_empty_argument("dataset")
def build_path(*, dataset):
    return f"/warehouse/{dataset}"

This deliberately narrow example requires a keyword argument. A general validator should use inspect.signature(func).bind(*args, **kwargs) or bind_partial to map positional and keyword arguments safely. Avoid hand-parsing arbitrary signatures unless necessary.

Authorization and registration patterns

Python · policy wrapper (illustrative)
from functools import wraps

def requires_permission(permission, authorizer):
    def decorate(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            # The authorizer is injected; no global identity is assumed.
            if not authorizer.has_permission(permission):
                raise PermissionError(f"Missing permission: {permission}")
            return func(*args, **kwargs)
        return wrapper
    return decorate

# Example wiring: permission service is supplied by the application.
@requires_permission("dataset:read", authorizer)
def read_sensitive_dataset(dataset_id):
    ...

Authentication/authorization decorators should make identity and policy sources explicit, execute authorization before any cached or sensitive result is exposed, and avoid treating a decorated Python function as a security boundary against arbitrary in-process code.

12 / Data engineering use

Applying decorators in data engineering

In a data platform, decorators are useful for cross-cutting function-level policies around extract, transform, validation and publish operations. They should improve consistency without hiding the pipeline's data semantics.

Common applications

OBSERVABILITY

Execution timing & metrics

Measure function duration, outcome and bounded labels for ingestion or transformation tasks. Do not log raw records or secrets.

RESILIENCE

Transient retry

Retry idempotent reads or writes with explicit idempotency controls, capped backoff and selected exception classes.

GOVERNANCE

Permission checks

Require a permission or data classification check before running a sensitive operation.

QUALITY

Input / output validation

Check required parameters or result invariants at stable function boundaries, and report failures consistently.

EFFICIENCY

Memoization

Cache deterministic, bounded metadata lookups. Avoid caching large mutable datasets or freshness-sensitive values by default.

REGISTRY

Task registration

Register handlers, validators or plugin functions at import/definition time, then execute them through a controlled registry.

Example: composable pipeline instrumentation

Python · separate concerns from transformation logic
from functools import wraps
from time import perf_counter
import logging

logger = logging.getLogger("pipeline")

def observe_step(step_name):
    def decorate(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            started = perf_counter()
            outcome = "success"
            try:
                return func(*args, **kwargs)
            except Exception:
                outcome = "failure"
                raise
            finally:
                logger.info("pipeline_step=%s function=%s outcome=%s duration_s=%.3f",
                            step_name, func.__qualname__, outcome,
                            perf_counter() - started)
        return wrapper
    return decorate

def require_batch_id(func):
    @wraps(func)
    def wrapper(batch_id, *args, **kwargs):
        if not batch_id:
            raise ValueError("batch_id is required")
        return func(batch_id, *args, **kwargs)
    return wrapper

@observe_step("normalize")
@require_batch_id
def normalize_batch(batch_id, records):
    return [record for record in records if record.get("id") is not None]

Note that the decorator signature should reflect the target contract. In the example, require_batch_id assumes the first argument is the batch identifier. It is intentionally not a universal method/function decorator; a production implementation should either formalize that signature or use inspect.Signature.bind.

13 / Delivery & operations

Testing, CI/CD & operational behavior

Decorators change the callable object seen by application code. Test both the wrapper policy and the observable callable contract. Most decorator defects are not syntax errors; they are semantic regressions in return values, exceptions, metadata, timing or ordering.

What to test

  • Arguments are forwarded exactly once per intended attempt, including positional-only and keyword-only parameters.
  • Return values are preserved, or any intentional transformation is explicitly documented.
  • Exceptions propagate unchanged unless the decorator contract says otherwise.
  • Metadata and introspection are preserved with wraps or update_wrapper.
  • Decorator application occurs at the expected definition time and does not trigger external I/O.
  • Stack order is tested where caching, auth, transaction, retry or logging are combined.
  • Async tests await the decorated function; generator tests fully iterate or close the iterator.
  • Retry tests use deterministic delays/randomness or injected sleep functions rather than slow real waits.
  • Concurrency tests cover shared decorator state where exactness or isolation matters.

Example: test a retry decorator without sleeping

Python · pytest-style test sketch
def test_retry_eventually_succeeds(monkeypatch):
    calls = {"count": 0}
    delays = []

    monkeypatch.setattr("time.sleep", delays.append)

    @retry(max_attempts=3, exceptions=(TimeoutError,),
           base_delay=0, max_delay=0, jitter=False)
    def operation():
        calls["count"] += 1
        if calls["count"] < 3:
            raise TimeoutError("temporary")
        return "ok"

    assert operation() == "ok"
    assert calls["count"] == 3
    assert delays == [0, 0]

This sketch assumes the retry decorator above and a module import path where the sleep function is patched correctly. In a mature library, inject the sleep and random functions as dependencies or patch the symbol where it is looked up. Keep the test focused on policy rather than elapsed wall-clock time.

Decorators are ordinary Python code and ship with the application/package. There is no special deployment mechanism. 14 / Efficiency

Performance, cost & design trade-offs

A wrapper adds at least one additional call layer and often incurs closure lookup, argument packing/unpacking, logging, metrics, locking or cache-key construction. Whether that overhead matters depends on call frequency and the cost of the wrapped operation.

Optimization rule. Measure before optimizing. For a database or network operation that takes tens or hundreds of milliseconds, a small wrapper cost is usually negligible. 15 / Trust boundaries

Security, privacy & reliability

Decorators often sit around privileged functions, so logging, authorization and retry policies must be designed with explicit data boundaries.

Security principles

  • Authorize before returning protected data. Confirm that cache layers cannot bypass authorization or mix results across identities/tenants.
  • Do not log secrets or payloads by default. Avoid logging credentials, access tokens, connection strings, row contents, personally identifiable values or unrestricted function arguments.
  • Inject dependencies. Pass an authorizer, logger or policy object explicitly rather than relying on hidden global state.
  • Preserve failures. Do not turn permission errors, data corruption or programming mistakes into silent success values.
  • Bound resource use. Limit retries, timeouts, cached entries, metric labels and retained references.
  • Do not treat decorators as a sandbox. Code running in the same Python process can often call underlying functions, inspect objects or alter state. Enforce authorization at the actual service/storage boundary.

17 / Architecture scenarios

End-to-end scenarios & design decisions

The following scenarios demonstrate how to reason about decorators in a production data-engineering codebase. The important skill is not to apply more decorators; it is to place each policy at the right boundary and retain clear failure semantics.

Scenario A — Resilient metadata ingestion

Requirement: Read a remote manifest, parse it and publish a batch status. Temporary network faults should retry; every attempt and overall outcome should be observable. Publishing the same batch twice must not create duplicate state.

Suggested call structure
Pipeline runnerbatch_id
→
Observeoverall duration
→
Retryread manifest
→
Transformvalidate manifest
→
Idempotent publishkeyed by batch_id

Design: Retry only the remote read if that read is idempotent and exceptions are transient. Make the publish idempotent at the storage/API layer using batch_id or an operation ID. An outer timing decorator can measure total observed duration; separate metrics can measure each stage.

Trade-off: Retrying the entire pipeline can repeat non-idempotent work. Prefer placing retry on the smallest operation with a well-defined retry contract.

Scenario B — Permission-aware cached dimension lookup

Requirement: A service exposes a small lookup function. Data access is tenant-specific, and permission can vary by user.

Design: Enforce authorization before returning any cached value. Either make the cache key include all security-relevant dimensions (tenant, identity or policy version as required) or cache only a tenant-neutral public value and apply authorization separately. Do not use a global memoization key that only includes a row/business identifier if different principals see different data.

!

Architect-level signal: “Put @lru_cache on the read function” is incomplete. Discuss authorization order, cache-key design, freshness, memory retention, cross-process behavior and invalidation.

Scenario C — Async API fetch fan-out

Requirement: Fetch multiple remote manifests concurrently. Each call has a per-attempt retry policy and async timing, but cancellation must work during shutdown.

Design: Use an async def wrapper that awaits the client operation, an async retry that awaits backoff, and a narrow exception tuple. Do not catch BaseException or swallow cancellation. Ensure concurrency is bounded by a semaphore or client limit; a decorator is not itself a concurrency limiter unless that is explicitly implemented.

Scenario D — Shared data-quality validation

Requirement: Many handlers need a consistent batch identifier and common output validation.

Design: Decorators can handle function-boundary checks, but schema validation often needs explicit data contracts and rich error reporting. Keep transformation and validation visible in function names or typed interfaces when they materially change data. Avoid hiding large data scans inside decorators because that makes execution order and lineage harder to reason about.

Architect decision checklist

  • Is this truly cross-cutting behavior shared by multiple callables?
  • Does it preserve the original signature, result, exceptions and cancellation semantics?
  • Does it apply at definition time or invocation time, and is that intended?
  • Does decorator order alter security, retries, transactions, caching or observability?
  • Does it support methods, class methods, static methods, async callables or generators as required?
  • Is all mutable state safe across threads/tasks and independent across decorated functions?
  • Can behavior be tested without external services, long sleeps or import side effects?
  • Would explicit composition or a context manager be clearer than a decorator?
18 / Interview bank

Interview questions & answers

Use the answers as a baseline, then explain the mechanism and trade-offs. Expand each question to review the response.

Beginner

Beginner What is a Python decorator?

A callable that takes an object—commonly a function or class—and returns a replacement or modified object. A common decorator creates a wrapper to add behavior around a function call without changing the function's core implementation.

Beginner Why can a function be passed to a decorator?

Functions are first-class objects in Python. They can be assigned, passed as arguments and returned from other functions. A decorator receives the function object as an ordinary argument.

Beginner What is the equivalent of @my_decorator?

For a function named work, it is equivalent to work = my_decorator(work). The returned object is bound to the name.

Beginner Does a decorator run on every function call?

The decorator application runs when execution reaches the decorated definition. A wrapper returned by the decorator typically runs on each subsequent call. A decorator factory expression may also run at definition time.

Beginner Why use *args and **kwargs?

They let the wrapper accept and forward arbitrary positional and keyword arguments. A wrapper with a fixed signature is only suitable for target functions matching that exact call shape.

Beginner Why must the wrapper return the wrapped function's result?

Without a return statement, the wrapper returns None. That silently changes the decorated function's contract even when the original function returns a useful value.

Intermediate

Intermediate What does functools.wraps do?

It applies update_wrapper to copy selected metadata from the wrapped callable, update the wrapper's attribute dictionary and add __wrapped__. This improves docs, debugging and introspection. Since Python 3.12, __type_params__ is copied by default.

Intermediate How do decorators with arguments work?

An outer factory accepts configuration and returns the actual decorator. The actual decorator receives the function and returns a wrapper. It is commonly described as a three-layer pattern: factory → decorator → wrapper.

Intermediate In what order are stacked decorators applied?

They are applied bottom-up. @a above @b is equivalent to func = a(b(func)). At call time, the outermost wrapper is entered first.

Intermediate How does a decorator work on an instance method?

A Python function stored on the class is a non-data descriptor. Access through an instance binds the instance as the first argument. A function wrapper remains a function descriptor, so self is forwarded in args.

Intermediate Why does a normal timer decorator fail for an async function?

Calling an async def function creates a coroutine object; it does not execute the coroutine body. A synchronous wrapper that times only the call measures object creation. Use an async wrapper and await the target.

Intermediate What is the difference between a class decorator and class-based decorator?

A class decorator is applied to a class definition and returns a class object or replacement, for example @dataclass. A class-based decorator is a class whose instance decorates a function, usually through __init__ and __call__.

Intermediate Why can lru_cache fail with a list argument?

The cache uses a dictionary-like key, so arguments must be hashable. Lists and dictionaries are mutable and unhashable. A stable immutable key may be appropriate only if converting it preserves the function's semantics.

Senior

Senior Why can a class-based decorator fail when applied to a method?

A callable instance with only __call__ does not automatically implement function descriptor binding. It may not receive the instance as self. Use a function-based decorator or implement __get__ to return a properly bound callable.

Senior When does decorator order create a security bug?

When a cache wrapper is outside an authorization wrapper, a cache hit can bypass the inner authorization check. Ensure authorization runs before protected results are returned, and design keys/invalidation around security context.

Senior Is lru_cache exactly-once under concurrency?

No. Its internal cache data structure is thread-safe, but multiple threads can call the wrapped function for the same missing key before the first result is cached. Thread safety does not imply single-flight execution.

Senior What changed for cached_property in Python 3.12?

The undocumented lock that previously guaranteed one getter execution per instance was removed. The old lock was per-property and could create contention. On Python 3.12+, concurrent access may run the getter more than once; add explicit synchronization if needed.

Senior Why is retrying a write after timeout dangerous?

A timeout does not prove the remote system failed to complete the operation. Retrying can duplicate a side effect. Use idempotency keys, conditional writes, unique operation IDs or transactions; retry only known transient exceptions.

Senior How can a decorator preserve the static callable signature?

Use ParamSpec to capture parameter types and TypeVar for the return type. Use Concatenate when injecting or removing a statically representable parameter. wraps helps runtime introspection but is not a substitute for accurate type annotations.

Architect / scenario-based

Architect A decorated ingestion write occasionally duplicates rows after retry. How do you redesign it?

First define the write's idempotency contract. Give each logical operation a stable key (for example, batch ID plus target partition), enforce uniqueness or conditional commit at the sink, and ensure ambiguous timeouts can be safely replayed. Narrow retryable exceptions, cap attempts and backoff, and instrument attempts separately from committed operations. Do not rely on the decorator to make a non-idempotent operation safe.

Architect You need timing for sync, async and generator handlers. How should a library expose it?

Either expose explicit decorators for each callable kind or implement a dispatcher that detects supported kinds and returns a wrapper with matching semantics. Test coroutine creation versus awaiting, generator creation versus full iteration, closure/exception behavior and introspection. State unsupported callable types clearly instead of silently timing only creation.

Architect A dimension lookup is cached globally, but output differs by tenant. What changes?

The cache key must include every dimension that affects the result, including tenant and possibly principal/permission version. Alternatively, cache tenant-neutral data and enforce access after retrieval. Choose a bounded cache with a documented freshness/invalidation policy. For multi-process deployments, remember that lru_cache is local to each process.

Architect The team has built 12 decorators around every task. What do you review?

Review whether each behavior is truly cross-cutting, whether nesting is readable, if a framework already provides middleware, and whether transactions, retries, auth and cache layers have correct ordering. Examine stack traces, import-time side effects, observability cardinality, per-call overhead, shared state and test coverage. Collapse redundant layers or use explicit orchestration/context managers where lifecycle is clearer.

Architect How would you roll out a new retry decorator across hundreds of jobs?

Start with an opt-in policy and inventory operations by idempotency and error class. Provide safe defaults, explicit allow-listed exceptions, bounded attempts/delay, metrics and structured logs. Test against representative clients, canary a small subset, compare retry volume and duplicate/failed outcomes, then expand. Keep a rollback switch and document per-operation overrides.

Architect Why might an explicit context manager be preferable to a decorator?

Use a context manager when the caller needs a visible lexical scope, access to a resource from __enter__, dynamic per-block setup, or precise lifecycle around a subset of statements. Decorators are cleaner when the entire callable shares a stable cross-cutting policy.
